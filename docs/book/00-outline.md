## 1. Introduction (`01-introduction.md`)

Opens with a one-paragraph framing of Lessley: a loyalty-optimization platform that reads a
user's real bank transactions through Open Finance and answers two questions — *which loyalty
clubs are you leaving money on the table by not joining*, and *what is the cheapest legal way
to pay for this specific cart right now*.

### 1.1 Background
The Israeli consumer-benefit landscape: discounts fragmented across employee clubs
(Behatsdaa, Hever), credit-card programmes (Mastercard, Isracard TopCash), retailer
programmes (HOT) and loadable gift-card networks (PaisPlus). Each publishes its own terms in
free-text Hebrew. Open Finance (PSD2-style regulated bank-data access) has recently made a
consumer's actual spending machine-readable for the first time.
*From:* `lessley-deals/src/lessley_deals/scraping/sources/` (the real source list),
`Lessley.Personalization/services/clients/open_finance_client.py`.

### 1.2 Problem Statement
Two concrete gaps: (a) a consumer cannot know which club membership would have paid for
itself, because that requires joining their spending history to a normalized deal catalogue;
(b) even knowing the deals, stacking them correctly is a combinatorial problem with
non-obvious legality rules — deals restrict what they combine with, and payment-instrument
deals cannot be chained at all because you cannot pay the same 400 ILS with two cards.
*From:* `deal-optimizer/README.md` reasoning, verified against
`deal-optimizer/src/deal_optimizer/tender.py` and `graph.py`.

### 1.3 Objectives
Measurable objectives derived from what the system actually does: normalize a multi-source
Hebrew deal catalogue to canonical store identities; enrich free-text terms into a structured
constraints schema; compute per-user spending insights and club matches from Open Finance
data; compute the cheapest legal deal combination for a cart; deliver all of it through a
single authenticated origin with no service-to-service HTTP trust.

### 1.4 Scope and Limitations
**In scope:** the six services, the scraping/matching/versioning pipeline, the optimizer
engine, the SPA, and the Docker Compose deployment. **Out of scope / known limits:** email is
an immutable cross-service key so email changes are unsupported; the user wallet is a mock
structure; the LLM constraints parser depends on a college-network-only endpoint; no mobile
app; deployment targets a single Compose host, not a cluster.
*From:* `lessley-cd/RUNNING.md:186-187`, `deal-optimizer/src/deal_optimizer/wallet.py`,
`lessley-deals/src/lessley_deals/enrichment/llm_client.py`.

### 1.5 Methodology
Iterative development against a fixed architectural contract (`instruction.md`): edge-only
entry, identity established once, no HTTP between services, shared collections with one
shape. Git with feature branches and pull requests (`git log` shows the PR-merge pattern),
Docker Compose for environment parity between dev and prod, per-language test suites
(xUnit, pytest, Vitest), skill-encoded conventions in `.claude/skills/`.

### 1.6 Organization of the Project Book
One short paragraph per chapter, as in example book B page 9.

**Diagram:** none in chapter 1 (example book A places its first figure here; I would rather
put the architecture diagram where it is discussed, in 3.1).

## 2. Literature Review (`02-literature-review.md`)

### 2.1 Overview of Relevant Literature
Per the spec, a single sub-chapter. Example book A treats it as ~3 pages of themed
sub-sections under one heading; I will do the same, with these themes:

1. **Microservice architecture and the edge-authentication pattern** — why identity at a
   single gateway/edge beats per-service authorization, and the IDOR class of bug that
   `X-Auth-Email`-only identity is designed to remove.
2. **Open Finance / open banking** as a data source for consumer financial applications.
3. **Entity resolution and fuzzy string matching** — Jaro-Winkler, Jaccard, token-set
   overlap, and the conservative auto-accept/review/discard threshold pattern the matching

5. **LLM-based information extraction** from unstructured terms-and-conditions text.
6. **Discount stacking as a constrained combinatorial optimization problem** — DAG shortest
   path, dynamic programming with state, and fractional knapsack (which is exactly what
   `tender.py` does).
7. **Slowly Changing Dimension Type 2** as the pattern behind `deal_versions`/`deals_current`.

## 3. System Design and Implementation (`03-...md`)

The longest chapter. This is where a reader who has never seen the repo learns what the
system is.

### 3.1 System Architecture
The six services and the one rule that shapes everything: **Caddy is the only public entry
point**. It terminates TLS, serves the SPA, strips any client-supplied `X-Edge-Key` /
`X-Auth-Email`, `forward_auth`s each edge-owned prefix against the Gateway's
`/api/auth/verify`, then stamps the verified identity inward. Personalization and
deal-optimizer are *edge* services, not Gateway-proxied services. The Gateway never calls
Personalization over HTTP — long-running recommendation work goes over RabbitMQ
(`lessley_events`, topic exchange, `Personalize.*` / `Gateway.*` routing keys) and comes back
to the client over SignalR. All three read-path services share one MongoDB database and read
the same `deals` / `stores` / `clubs` / `mccs` collections — one shape, no projected copies.
Design principles to name explicitly: single origin (no CORS, `SameSite=Strict` works),
defence in depth, layered Controller → Service → Repository, Protocol/interface boundaries.
*From:* `lessley-cd/Caddyfile:24-114`, `instruction.md:15-42`,
`Lessley.Gateway.Api/Program.cs:110-164`, `Lessley.Personalization/main.py:359-371`,
`deal-optimizer/src/deal_optimizer/edge_auth.py`, `.../auth.py`.

### 3.2 Data Collection and Preprocessing
This sub-chapter is the scraping pipeline, and it maps onto the spec almost word for word.
**Collection:** async scrapers, one adapter per source, registered in `registry.py`; three
fetch strategies (httpx, curl-cffi, Playwright/Selenium) plus a generic LLM scraper for sites
with no clean API; raw records persisted verbatim and frozen for auditability and replay.
**Preprocessing:** the six-step normalization pipeline (text cleanup → Hebrew normalization →
store-name extraction → price parsing → deal-text clean → date parsing) producing an
immutable `NormalizedRecord`. **Quality/accuracy:** the six-stage match pipeline with
conservative thresholds (auto-accept ≥ 0.90, review ≥ 0.50, discard below), the human review
TUI, and the alias learner that feeds confirmed decisions back so the next run auto-matches.
**Challenges:** Hebrew name variance; group gift cards that belong to a chain rather than a
store; deduplicating identical boilerplate terms before LLM enrichment; guarded expiry rules
so a partial scrape cannot mass-expire the catalogue.
*From:* `lessley-deals/src/lessley_deals/{scraping,normalization,matching,review,versioning}/`,
`lessley-deals/docs/{architecture,matching,orchestration,group-deals}.md`. Every threshold and
stage count will be read out of the code, not the README — see **Q3**.

### 3.3 Implementation Details
Per-service walkthrough with short, real code excerpts (cited by `path:line`):

- **Gateway (C# / .NET 8)** — controllers as thin handlers, services own logic, EF Core with
  the MongoDB provider, JWT in an HttpOnly cookie plus a CSRF token, the middleware order in
  `Program.cs`, MassTransit consumers, the SignalR hub and its email-keyed user-id provider.
- **Personalization (Python / FastAPI)** — DI container, insights and recommendation
  services, Beanie documents, the aio_pika publishers, `EdgeAuthMiddleware`, and the
  `authenticated_email` dependency that refuses an `email` parameter by construction.
- **deal-optimizer (Python)** — the engine proper: the lean schema and legacy adapter, the
  layered order `store_sale → member_discount → coupon`, bilateral edge legality, the
  state-tracking DP that re-validates every (new, prior) pair, `max_deals` pruning *during*
  the search, and the separate tender phase that solves gift-card/payment/cashback deals as a
  bill-splitting problem instead of chaining them.
- **CategoriesEnricher (Python / FastAPI)** — LLM-backed transaction/store/deal
  classification over RabbitMQ.
- **lessley-deals (Python)** — the scheduler worker: one asyncio loop per source, Mongo lease
  locks, run journal, hard timeout, exponential backoff with jitter.
- **Frontend (React / TS)** — feature-first layout under `src/features/`, the relative-URL
  API client with CSRF header and single 401 refresh-retry, route guards, SignalR hook.
- **Software and hardware specifications** — the spec explicitly asks for both: language and
  framework versions, MongoDB / RabbitMQ / Loki / Grafana / Caddy, container ports
  (5001/5002/5003), the three run modes, and the deployment host. Hardware: see **Q4**.

## 4. Results and Analysis (`04-...md`)

> **Q5 resolved — measure what exists.** The spec asks for experiments, descriptive
> statistics, means and confidence intervals, and a comparison table against existing
> approaches. Lessley is an engineering platform, not a research study: there are no benchmark
> runs, no user study, no measured latencies and no accuracy figures anywhere in the repo, and
> none will be invented. Instead the chapter reports only measured output, produced by running
> stated commands:
> - **Real test-suite results** — I can run `pytest` (deal-optimizer, Personalization,
>   lessley-deals), `dotnet test` (Gateway) and `npm run test:run` (frontend) and report the
>   actual pass/fail counts as measured output, with the command and date.
> - **Worked optimizer examples** — the engine is deterministic, so I can run real carts
>   through it and report the exact stacks and savings it returns. That is measurement, not
>   invention.
> - **Catalogue statistics** — counts of sources, deals, stores and matched/review/unmatched
>   records, computed from the actual data files or a live Mongo query.
> - **A qualitative capability comparison** against existing consumer options (manual
>   comparison, per-club apps, cashback aggregators) — a feature table like example book A's,
>   explicitly labelled qualitative so it is not mistaken for a performance benchmark.
>
> Failing tests are reported with their output, not excluded. No mean, standard deviation or
> confidence interval appears unless a real repeated measurement backs it.

### 4.1 Experimental Setup

### 4.3 Data Analysis and Interpretation
What the numbers say — where matching is confident and where it defers to review, which deal

### 4.4 Comparison with Existing Approaches
Qualitative capability table versus manual coupon hunting, single-club apps and cashback

### 4.5 Discussion of Findings
Implications, and an honest statement of limitations: catalogue freshness depends on the
scrapers; LLM enrichment silently degrades if the model endpoint is unreachable; the wallet is
mocked; results were not validated against real checkout receipts.
